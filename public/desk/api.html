API

Everything the lab page shows is computed from this API: one call per model per notice for the evaluation, and the triage endpoint with a policy of your choice for production-style use. Described in OpenAPI 3.1.

A fictional demo. Do not send real personal data. The API is open with rate limits; in production it would sit behind the platform's API gateway and identity provider.

Endpoints

MethodPathWhat it does
POST/api/v1/triageTriage one notice, a sample by id or your own text, through a policy: one model key, or cheap>strong with the router between them. Default haiku>sonnet.
POST/api/v1/runOne model on one sample notice or attack. The evaluation calls this for every pair; answers are cached per prompt and sample version.
GET/api/v1/modelsThe ten models with family, size, number format, list prices, and the Workers AI id that answered the last probe.
POST/api/v1/probeAsks each Workers AI candidate id for one word and remembers which ones this account can run.
POST/api/v1/batchQueue every sample notice in one Claude Message Batch at half the price. Up to 3 a day.
GET/api/v1/batch/{id}Batch status; once it has ended, the validated results for every notice.
POST/api/v1/feedbackThe moderator's decision next to the proposal. Feeds the override rate.
GET/api/v1/metrics?days=14Daily counters, calls per model included, for the monitoring page.
GET/api/v1/healthStatus, default policy, model keys, prompt and sample versions, limits.

What comes back from triage

      
    
        
  • route: every model step with category, confidence, verified and rejected values, whether the JSON was broken, cost and time, and the reasons the router gave for escalating.
    • 
        
  • facts: URLs, notifier, statements, each with the exact quote and its span. Only verified values are here; the rest is in rejected with the reason.
    • 
        
  • injections: passages that try to instruct the system, flagged by rules, the model, or both.
    • 
        
  • decision: the proposed action, priority, deadline, the Article 16 checklist and what is missing.
    • 
        
  • statement: when content would be removed or disabled, a draft statement of reasons in the format of the EU DSA Transparency Database, for a moderator to approve.
    • 
      

    


    

      
Errors and limits

      
    
        
  • 400 invalid input, with a code such as empty, too_long or unknown_model.
    • 
        
  • 429 rate_limited after 6 own runs a day per IP, 3 batches or 6 probes a day; budget when the daily cap on fresh model calls is used up.
    • 
        
  • 410 model_retired when a model Workers AI has retired would need a fresh call. Its recorded answers on the sample notices are still served.
    • 
        
  • 502 model_error with the upstream error text, never a key. Not cached, safe to retry. A model that answers with broken JSON is not an error: that answer is recorded, because it is a result.
    • 
      

    


    

      
What production would add

      
    
        
  • Authentication through the platform's API gateway and identity provider instead of open access.
    • 
        
  • A queue between intake and triage, the batch path for backlogs and the live path for urgent categories.
    • 
        
  • The evaluation as a release gate: re-run on every prompt, model or router change, with the policy chosen from the result rather than by hand.
    • 
        
  • Statements of reasons submitted to the Transparency Database API after approval, and metrics in a real store with alerting.
